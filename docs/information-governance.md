# 公开信息治理与隐私保护规范

本文件规定 ExamPilot 在公开交付中的信息分级、审查范围与推送前门禁。适用于所有开发、审查、测试、提交、推送、合并及发布任务。

**基本原则：内部研发信息默认不公开；对外发布遵循最小必要披露。** 公开交付以产品、技术实现、可验证的测试结果和正式维护记录为核心，不将私人工作过程复制为公开文档或 Git 历史。

---

## 1. 信息分级

### PUBLIC — 允许公开

- 产品功能、架构与技术设计
- 正式源代码、必要测试及契约
- 可复现的测试方法与真实验证结果
- 用户文档、技术文档及 Release Notes
- 软件版本、兼容性与已知限制
- 必要的许可证、第三方声明及正式作者署名
- 经过确认可以公开的安全与维护信息

### INTERNAL — 默认不得公开

- 内部工具、协作方式与工作流程
- 任务分工、内部沟通记录与私人偏好
- 内部协作记录与专用验收日志
- 本地用户名、电脑名称、磁盘绝对路径
- 私有仓库名称、内部工作区及非公开链接
- 内部截图、调试日志、实验记录和临时目录
- 无公开必要的个人身份及环境信息

上述内容可以保存在授权的内部记录中，但不得未经审查进入公开仓库。

### SECRET — 禁止提交和传播

- API Key、Token、密码和凭据
- 私钥、会话令牌、敏感环境变量
- 真实用户数据库、个人文件及备份
- 未授权公开的个人数据或第三方机密

敏感值不得进入 Git、日志、PR、Issue、CI Artifacts 或 Release。

---

## 2. 公开内容写作规范

公开文字必须使用专业、中立、客观的工程表述，不无必要地披露内部工具或协作方式。

| 避免 | 推荐 |
| --- | --- |
| 「某工具/某人已完成代码」 | `Implemented and verified` |
| 「某验收工具宣布 PASS」 | `Regression tests passed` |
| 「用某模型修复了该问题」 | 描述缺陷现象、根因与修复方式 |
| 无依据的 `independently validated` | 仅在**确有独立验收证据**时使用，并注明证据来源 |
| 泛泛的「已通过测试」 | 写明命令、范围与结果，如 `CI passed on commit <sha>` |

不得通过删除工具名称而伪造验收事实，不得把开发者自验包装为独立验收。

产品实际依赖的 AI SDK、Provider 协议、合法第三方依赖及必须保留的许可证信息，不属于应隐藏的内部开发记录。

---

## 3. 审查范围

公开信息审查必须覆盖：

- README、文档、代码注释和测试数据
- Git Commit 标题与正文
- Branch 名称
- Pull Request 标题、描述与评论
- Issue、Discussion 及审查记录
- Changelog、版本标签与 Release Notes
- 截图、附件、构建产物和 CI Artifacts
- 配置文件、元数据和文件名

不得只检查源代码而忽略托管平台页面上公开的文字和附件。

---

## 4. 推送前门禁

任何公开交付之前必须完成：

1. 确认目标仓库及公开范围
2. 检查新增、修改和拟提交的文件
3. 检查 Commit Message、PR 描述及 Release Notes
4. 扫描敏感凭据、私人路径、个人信息和内部开发记录
5. 移除无必要的内部信息，保留正确的技术事实
6. 确认许可证、正式署名和必要的来源声明完整
7. 确认测试、CI 与版本状态真实且对应正确提交

发现隐私风险或敏感信息时，应先停止相关公开操作，完成审查后再继续。不得为赶进度跳过此门禁。

### 自动化检查

工具：`tools/public-info-check.mjs`。**扫描内容与扫描提交元数据是两件不同的事，输出中分别报告。**

| 模式 | 扫描的内容 | 适用场景 |
| --- | --- | --- |
| （默认）`--index` | **暂存区**中每个文件的完整内容 | 本地提交前检查将发布的内容 |
| `--worktree` | 工作区文件内容 | 快速自查 |
| `--commit <rev>` | 该提交树中每个文件的完整内容 | CI 检查实际提交内容 |
| `--all-refs` | 所有 ref 可达的**去重 Blob** 内容 | 维护者全量审计 |

各模式的输出会注明实际取得的内容范围与数量。**除 `--all-refs` 外，都不会扫描历史提交中的全部文件内容。**

三种检查对象分别处理：

- **当前/暂存内容**：默认检查暂存区，因此「暂存后修改工作区」不会造成漏检；CI 使用 `--commit HEAD` 检查实际提交内容。
- **提交元数据**：单独扫描提交信息，与内容扫描分开报告，并注明**元数据范围**（`HEAD` / 所选修订的祖先 / 全部 ref）。`--commit <rev>` 按所选修订扫描其祖先提交，不固定读取 `HEAD`；可用 `--no-metadata` 关闭。
- **禁止提交的文件路径**：`data/bank.json`、`data/local-bank.json`、`src/lib/local-bank.generated.ts`、`tools/pdf_text.txt`、`server/ai-config.json`、**全部 `.env` 及点号变体**（`.env.local`、`.env.production.local`、`.env.development.local` 等，任意层级、不区分大小写）、私人来源 PDF，以及本地专用产物（`tools/.gh_token`、`tools/staged.txt`、`exampilot-bank.json`、`exampilot-history-*.csv`、`scratch/` 等），**按路径硬阻断**。`.gitignore` 可被 `git add -f` 绕过，因此不依赖它。明确允许的无凭据模板为 `.env.example`、`.env.sample`、`.env.template`。

锁文件（`package-lock.json`、`npm-shrinkwrap.json`）**不是扫描盲区**：其中的 `SECRET` 规则照常执行，仅跳过易产生噪音的词汇类规则（注册表 URL 与完整性哈希不构成作者披露）。

### 文本匹配的三种形式

单纯按行匹配「字面量」会漏掉同一内容的另一种写法。因此每一行同时按**原文、转义解码后（`\uXXXX` / `\xXX`）、拼接展开后（`'a' + 'b'`）**三种形式匹配。这三种形式是同一处历史暴露的直接教训：该处把文档名拆成转义片段，任何单一形式都看不出它是文件名。

**解码是主要手段，「看起来像编码」不是。** 早期版本把「一行里有多个 `\uXXXX`」本身当作违规，这会误伤合法的国际化文案表、断言转义的测试、以及被转义的标点。判定标准应当是**解码后的内容是否属于不可公开的信息**，而不是书写形式。因此现有规则只保留一条无法用其他方式表达的窄信号：**跨字符串拼接的转义文本**（把若干 `\uXXXX` 片段用 `+` 连接成一句话），因为那正是历史暴露所用的形状；普通的转义字面量不再被阻断。

### 占位符豁免只作用于「被匹配到的值」

`assigned-secret` 等规则的豁免检查**匹配到的值本身**，而不是整行。早期版本只要整行任意位置出现 `example` / `sample` / `xxx` 就放行，因此真实凭据旁边有一句注释即可通过。本地路径与邮箱同理，只豁免已发布的占位段（如 `syntheticuser`）。

### 凭据赋值必须覆盖三种书写形态

`assigned-secret` 必须同时识别**带引号**与**不带引号**的赋值：

```
AI_API_KEY=<值>        .env —— README 指导用户创建的形态
"apiKey": "<值>"       JSON —— 网关配置文件的形态
apiKey: <值>           YAML
const apiKey = '<值>'  JS / TS 字面量
```

早期版本只匹配带引号的字面量，因此 `.env`、JSON 与 YAML 三种形态**全部漏检**。这并不是理论缺口：本项目真实的配置正是 JSON 与 `.env`，而**没有已知提供商前缀的自托管网关令牌**也无法被 `credential-literal` 的前缀表捕获，两道防线会同时失效。现已补齐无引号分支。

无引号分支刻意收窄，以免把普通代码变成阻断项：值需为 20 字符以上的单一不透明串（仅字母、数字、`_`、`-`，或 JWT 形态），因此 `process.env.AI_CONFIG_TOKEN`、`key={item}`、`String.fromCharCode(...)` 与 `max_tokens: c.maxTokens` 都不命中；凭据名仍限定为 `api` 开头的拼写，React 的 `key=` 属性不会被误读。回归测试对**每一种形态**都给出正例（必须阻断）与反例（必须放行），并用变异检验证明这些用例确实有约束力——只加规则不加反例，或用例无法失败，都会形成虚假覆盖。

### AI 工具名与 AI 参与说明

**普通 AI 助手名、provider 名、模型标识符，以及「assisted by …」这类如实说明 AI 参与的表述，都属于 PUBLIC/REVIEW，不阻断构建。**

早期版本把任何工具名都判为 INTERNAL，这是双重错误：一方面把公开产品名当成秘密，另一方面**惩罚披露、奖励沉默**——正好与信息治理的目的相反。本规范明确禁止掩盖 AI 参与，因此如实署名必须被允许。

真正需要保护的是**私人协作记录**，而不是工具名本身。以下才判为 INTERNAL：

| 判为 INTERNAL | 判为 PUBLIC / 仅提示 |
| --- | --- |
| 对话/聊天记录、会话转录（`… 聊天记录`、`chat log`、`transcript`） | 工具名、provider 名、模型 ID |
| 写给某工具的个人提示词（`my prompts for …`） | 「assisted by …」等真实署名 |
| 内部指令文件（`内部工作流`、`internal instructions for …`） | 集成文档、API 端点、协议说明 |

输出安全：命中项**只输出规则 ID、路径与规则说明，绝不输出匹配到的原文**，避免把检测到的凭据、私人路径或个人信息再次写入 CI 日志。据此，**文件名本身即私人信息的路径（如私人来源文档）一律遮蔽为「redacted path」**；固定且通用的路径（`data/bank.json`、`.env.production.local`）照常显示，因为指出它们不泄露任何私人内容，且便于修复。

严重级别：`SECRET` / `INTERNAL` 命中与禁止路径均使构建失败；`REVIEW` 级仅提示，需人工确认。

**`--all-refs` 是维护者诊断工具，不作为合并门禁。** 它会扫描所有 ref 可达的去重 Blob，因此可能报告历史提交中的残留——即使当前 `main` 的正文已经清理干净。普通新提交无法清除历史信息，所以该模式本就应当能够报告它们；出现非零退出码时，应判断是「历史残留」还是「本次交付引入」，而不是调整规则让其通过。CI 使用的是 `--commit HEAD`，检查本次交付的实际内容。

CI 中的执行步骤位于 `quality` Job 内（该 Job 名称是 `main` 分支保护的必需检查，不得重命名）：

```bash
node tools/public-info-check.mjs --commit HEAD   # 实际提交内容（本次交付）
npm run test:public-info                          # 门禁自身的回归测试
npm run test:release                              # 产物校验器的回归测试
npm run build:public                              # 公开构建 + 交付清单校验
```

**自动化检查只能发现已知模式，不能替代人工审查；一次通过不构成安全保证。**

### 交付产物边界（源码干净不等于产物干净）

源文件全部合规，**不代表构建产物合规**。`src/lib/bank.ts` 静态导入生成器 `src/lib/local-bank.generated.ts`；在一台装有完整课程题库的机器上执行 `npm run build`，**该题库会被打进 `dist/`**——从仓库里完全看不出来，上传产物就会公开它。

因此发布前必须用 `npm run build:public`：它先以 `--public` 写出空加载器（即使本机有完整题库），再构建，最后用**正向交付清单**校验产物本身。`npm run verify:release` 可单独对已有产物运行。

校验采用**白名单**而非黑名单：明确要求产物中**必须**包含公开示例题库的每一道题，并且**不得**包含其他题库的题干、题库元数据（`source` 字段即来源文档名）、Source Map、本机绝对路径或凭据形态字符串。白名单是刻意的——黑名单只能拦住有人记得写进去的东西。

> **注意**：私人题库的 `source` 字段本身就是来源文档名。即使一道题都没被嵌入，该字段单独泄露也构成暴露，因此产物校验把它与题干分别检查。

## 5. 已公开信息的处理

如果发现信息已经进入公开仓库：

1. 首先确认信息类型、影响范围与严重程度
2. 对当前源码和文档进行安全修正
3. 对可编辑的公开 PR、Issue 和说明进行必要整改
4. 如涉及真实凭据，立即报告并制定撤销、轮换与补救方案
5. 检查历史 Commit、Tag、Release 和公开附件中的残留
6. **不得声称普通新提交能够清除历史信息**
7. 未经用户明确批准，不得 Force Push、重写历史、移动 Tag 或破坏已有发布记录

对于无法通过正常方式清除的历史信息，应准确报告残留及风险，由用户决定后续处理方式。**不得把「当前正文已清理」表述为「历史已清除」。**

---

## 6. 内部与公开仓库隔离

当项目同时存在内部仓库和公开仓库时：

- 内部仓库可以保留必要的研发、协作和决策证据
- 公开仓库只接收审查通过的正式交付内容
- 不得直接将内部仓库历史、文档和私有文件整体推送到公开仓库
- 公开交付应采用经过审查的文件范围和正常 Git 流程

本项目特别约定：**完整课程题库、原始 PDF 及其派生文件永不进入公开仓库**，公开仓库只包含自行编写的示例题库。详见 [CONTRIBUTING.md](../CONTRIBUTING.md)。

---

## 7. 验收标准

只有满足以下条件，才能报告 `PUBLIC_READY`：

- [ ] 公开内容不包含未经批准的私人或内部信息
- [ ] 未发现未处理的敏感凭据泄露
- [ ] Commit、PR、文档及发布说明均经过审查
- [ ] 工程验证结果准确、可追溯
- [ ] 许可证和必要公开信息完整
- [ ] 已知历史暴露问题得到明确记录和处理决定

**`PUBLIC_READY` 不等于仓库历史中的一切信息已被永久消除。**

任何未确认项目必须标记为未验证，不得猜测或默认安全。

---

## 8. 执行权限

本规范允许进行检查，但**不构成** Commit、Push、Tag、Release 或历史修改的授权。这些操作仍须遵守项目既有授权与数据安全规则。

如本规范与其他项目指令存在冲突，优先保护数据安全和用户隐私，并在发布前明确报告冲突。
